# S/W Version 관리 정책

## 1. 목적

여러 레포로 나뉜 프로젝트들의 버전을 각 레포별로는 독립적으로, 시스템 전체로는 일관되게 추적하기 위한 규칙을 정의합니다.

## 2. 적용 범위

Github Organization 산하 모든 Source 레포에 적용됩니다. (문서 전용 레포, 인프라 설정 레포는 필요 시 선택 적용)

---

## 3. 버전 체계 개요

버전은 **두 개의 레이어**로 관리합니다.

| 레이어             | 대상                        | 체계                          | 관리 위치                          |
| ------------------ | --------------------------- | ----------------------------- | ---------------------------------- |
| ① 컴포넌트 버전    | 개별 레포                   | SemVer (`vMAJOR.MINOR.PATCH`) | 각 레포의 Git Tag / GitHub Release |
| ② 통합 릴리스 버전 | 전체 시스템(여러 레포 조합) | CalVer (`YYYY.MM.PATCH`)      | `release-manifest` 레포            |

개별 레포는 자기 기능/수정 이력에 따라 자유롭게 버전이 오르고, 통합 버전은 "이 시점에 어떤 조합으로 배포했는가"의 스냅샷 역할만 합니다. 두 체계를 섞지 않는 것이 핵심입니다.

---

## 4. 컴포넌트 Type과 버전 영향 매핑

| Type                                        | 설명                    | 버전 영향        |
| ------------------------------------------- | ----------------------- | ---------------- |
| `feat`                                      | 새 기능 추가            | **MINOR**        |
| `fix`                                       | 버그 수정               | **PATCH**        |
| `perf`                                      | 성능 개선               | PATCH            |
| `!` 접미사 또는 footer의 `BREAKING CHANGE:` | 하위 호환성 깨짐        | **MAJOR**        |
| `docs`                                      | 문서 변경               | 없음             |
| `style`                                     | 포맷팅 (로직 변경 없음) | 없음             |
| `refactor`                                  | 동작 변화 없는 리팩토링 | 없음             |
| `test`                                      | 테스트 추가/수정        | 없음             |
| `build`                                     | 빌드/의존성 변경        | 없음             |
| `ci`                                        | CI 설정 변경            | 없음             |
| `chore`                                     | 기타 잡무               | 없음             |
| `revert`                                    | 커밋 되돌림             | 되돌린 커밋 기준 |

---

## 5. 브랜치 전략

| 브랜치         | 역할                                                   |
| -------------- | ------------------------------------------------------ |
| `main`         | 항상 배포 가능한 최신 상태. 머지 시 자동 릴리스 트리거 |
| `feature/*`    | 기능 개발, `main`에 PR로 머지                          |
| `release/x.y`  | (필요 시) 릴리스 안정화 브랜치                         |
| `hotfix/x.y.z` | 긴급 패치, `main`과 해당 `release` 브랜치 양쪽에 반영  |

---

## 6. 레포별 릴리스 프로세스

1. PR 머지 (Conventional Commits 준수)
2. CI에서 커밋 이력 기반으로 다음 버전 계산
3. Git Tag 생성 (`v1.4.2`)
4. GitHub Release 발행 (Release Note = Changelog 자동 생성)
5. 레포 내 `CHANGELOG.md` 갱신 (Keep a Changelog 포맷)
